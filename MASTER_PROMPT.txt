JECTIVE Robotics Studio Master Prompt
You are the coding agent responsible for designing, implementing, testing, packaging, and documenting JECTIVE Robotics Studio. Build a real Windows 10 and Windows 11 desktop robotics IDE for students, teachers, schools, and universities. Deliver working software and reproducible evidence, not a concept, website mockup, product specification alone, or presentation. Use Electron, React, and TypeScript for the desktop application, Blockly for visual programming, Monaco for Arduino C++ editing, and the actual Arduino CLI for compilation and flashing. The educational kit uses an ESP32-family controller connected to a provisional JECTIVE carrier board. Its final board revision, pin assignments, motor driver, sensors, and mechanical parts are not yet known. Treat these as explicit hardware assumptions, while making the software architecture and implemented workflows real.
This entire document is one master prompt and one implementation contract. Its sections belong to the same task. Read it completely, preserve its requirements across phases, and implement them in a repository. Do not ask the user to type “continue” between sections. If an execution limit interrupts work, save an accurate handoff and resume from verified repository state. Never describe unfinished work as complete. Use English for source identifiers and engineering documentation; provide the product UI and required learning content in English, Kazakh, and Russian.
1 Mission and nonnegotiable delivery rules
The core learner journey is to install the EXE, open the application without internet, choose a supported or clearly provisional robot profile, follow an assembly guide, complete a lesson, create a block program, inspect its generated Arduino C++, simulate supported behavior, compile it with a real toolchain, explicitly select a serial device, flash compatible hardware, and inspect actual serial output. The teacher journey is to prepare assignments, distribute portable classroom packages, collect submissions, review progress and evidence, and export results without requiring a cloud account.
Every visible action must do its advertised work. Prohibit fake buttons, fabricated device lists, random sensor readings presented as hardware data, prerecorded “live” telemetry, artificial build progress, hardcoded “compile successful” messages, timers that pretend to upload firmware, empty lesson pages, placeholder documentation, lorem ipsum, and demo-only classroom statistics. Fixtures and mocks are allowed inside automated tests or a separately labeled demonstration mode only. They must never be selected silently in the shipping hardware path.
Distinguish implementation status from verification status. Track software implementation, automated test results, actual compiler results, simulated behavior, upload results, runtime handshakes, and physically observed behavior independently. “Compiled” means the real compiler exited successfully and produced the expected artifacts. “Uploaded” means the real uploader completed successfully for the explicitly selected device. “Firmware connected” means a compatible runtime handshake was received. “Physically verified” requires a dated test on identified hardware with recorded observations. One status must not imply another.
When hardware, credentials, signing certificates, network access, or a Windows test environment are unavailable, finish all independent work and record the exact blocked verification. Hardware tests that did not run are NOT RUN, never PASS. A simulator-only implementation cannot be called a hardware-ready release. Do not invent certificates, vendor specifications, electrical ratings, test logs, or user approvals. Make sensible reversible implementation decisions autonomously; ask only when a consequential decision genuinely cannot be inferred.

The renderer uses nodeIntegration disabled, contextIsolation enabled, sandbox enabled, a restrictive Content Security Policy, and packaged local assets. Validate IPC senders and origins, constrain navigation and new windows, and do not expose raw ipcRenderer, arbitrary filesystem access, arbitrary command execution, or generic privileged method dispatch.
Run expensive parsing, simulation, indexing, and compilation orchestration outside the UI thread. Use workers or managed child processes with bounded messages and cancellation. Use structured errors with stable codes, localized explanations, actionable recovery steps, and redacted diagnostic details. Include operation IDs so a late result cannot overwrite the state of a newer operation.
Model long-running operations as state machines. Compilation, upload, serial monitoring, and simulation need explicit idle, starting, running, cancelling, succeeded, failed, and interrupted states where appropriate. Serialize operations that compete for one device or toolchain directory. Make event subscriptions disposable; close workers, ports, timers, and child processes on shutdown. Reopening a panel must not create duplicate listeners or duplicate motor commands. Persist only durable state, not stale “connected” or “running” flags.

5 Modular board and component profiles
Implement versioned, schema-validated, data-driven profiles with stable IDs. Separate board definitions, carrier revisions, component definitions, robot assemblies, and project wiring. A board profile describes MCU family, supported Arduino FQBN and options, required core version, toolchain constraints, upload transport, flash parameters, reset behavior, serial defaults, and real pin capabilities. A component profile describes required interfaces, electrical assumptions, units, driver implementation ID, library versions, calibration parameters, safe states, and optional simulation model. An assembly profile composes these into logical roles and geometry.
Represent pin aliases, allowed GPIO capabilities, input-only pins, reserved or boot-sensitive pins, ADC constraints, PWM channels or allocation requirements, I2C addresses and buses, SPI signals, UART use, voltage expectations, polarity, and shared-resource constraints where applicable to the selected MCU. Never assume all ESP32 variants share the same pins or peripheral APIs. Validate conflicts, duplicate I2C addresses, unsupported interfaces, impossible pin directions, and unassigned required pins before generation or upload. Include override paths for expert users only when the condition is actually overridable; hard electrical incompatibilities remain blocking.
Ship a clearly labeled JECTIVE Prototype profile and a separately identified generic ESP32 development-board reference profile based on an explicitly selected real board definition. Do not invent an official JECTIVE pinout. Unknown JECTIVE wiring remains unassigned and prevents hardware upload until a user supplies and validates a mapping. A profile may be fully usable in the simulator without becoming electrically validated. Show profile provenance, version, assumptions, validation status, and compatible content in the UI.
Provisional component families may include two DC motors with a dual H-bridge driver, line sensors, a distance sensor, buttons, LEDs, a buzzer, a servo, encoders, and an optional IMU or display. Do not require all of them for basic use. Support substitution through capability interfaces and driver adapters. Code generation, firmware, guides, simulator models, and lesson compatibility must read the same profile data rather than maintaining conflicting hardcoded pin maps. Adding a second motor driver must not require rewriting the editor or curriculum engine.
Profiles must be declarative data. Never execute scripts or dynamically load native libraries from imported profile files. Map approved driver IDs to reviewed implementations packaged with the application. Validate imported profile archives, show a diff before replacement, preserve older versions for existing projects, and provide explicit migrations. Store the resolved profile version and hash in each project and build manifest so profile updates cannot silently change wiring.

10 Serial devices and firmware protocol
Implement real serial enumeration, refresh, hot-plug events or reliable polling, explicit port selection, baud settings, opening and closing, and a monitor with timestamps, line endings, clear, pause display, search, and export. Provide bounded buffering and backpressure so a noisy device cannot freeze the IDE. Plot only actual parsed numeric telemetry or explicitly labeled simulator telemetry. Show invalid packets and connection errors without fabricating values.
VID, PID, device names, and a remembered COM number are hints, not proof of board identity. Display available identifiers and require explicit selection when ambiguous. Handle two identical boards, COM changes after reset, disappearing devices, access-denied errors, ports held by other applications, and reconnect without automatically rearming motors. Manage exclusive ownership so serial monitoring closes before upload and resumes only after upload and the appropriate reconnect policy. A reconnect must not trigger an upload or replay queued movement.
Define a versioned, bounded protocol for compatible JECTIVE firmware: hello and capabilities, firmware and profile versions, device/session identity, telemetry, heartbeat, command ID and sequence number, acknowledgement, error, arm, disarm, and stop. Choose a documented framing scheme with maximum message sizes and malformed-frame recovery. Separate protocol frames from ordinary student Serial.print output or define safe multiplexing. Reject duplicate or stale actuation requests and use device-side receipt time for freshness. Do not depend on synchronized PC and robot clocks.
Generic Arduino sketches may not implement this protocol. In that case retain raw serial monitoring and show “custom firmware without JECTIVE safety handshake.” Disable live JECTIVE motor controls and protocol-dependent features instead of pretending compatibility. A successful upload alone does not prove the flashed firmware is running or that a sensor is connected correctly.
11 Safe motor firmware and runtime
Implement a reusable Arduino-compatible JECTIVE runtime with board and component adapters. Define unambiguous motor units, signed duty ranges, direction conventions, deadband, acceleration limits, braking versus coasting behavior, sensor units, calibration, and error returns. Keep driver-specific GPIO and peripheral code outside student lesson logic. Match the selected Arduino ESP32 core APIs, including PWM differences between versions, through tested adapters.
Default to disarmed with motor enables inactive at boot, reset, initialization failure, protocol mismatch, and relevant fault. Require explicit arm for live host-controlled motion. Never arm automatically after reconnect or recovery. Clamp speed and duration, apply bounded acceleration, insert a safe zero-output interval before direction reversal when required by the driver, and reject invalid commands. A UI Stop button sends the highest-priority stop request and clears pending motion, but the firmware must enforce safety without relying on the renderer or USB connection remaining alive.
For live control, start with a configurable conservative host heartbeat interval of 100 ms and a device-side stale-command timeout no greater than 500 ms; document these as design targets to validate, not certified guarantees. On timeout, disarm and drive outputs to the profile's defined safe state. Refresh motion authority only on valid fresh commands from the active session. A backlog of heartbeats must not keep old motion alive. Implement a watchdog or independent safety task appropriate to the MCU; test deadlocks, reset behavior, timer rollover, malformed frames, and loss of host communication.
Distinguish tethered live control from explicitly launched autonomous student programs. An autonomous program must not require a PC heartbeat merely to run, but must obey runtime motor limits, fault handling, bounded operations, and an available physical stop path. For block programs, generate cooperative scheduling or a state machine so delays and loops do not starve safety checks. Avoid long blocking sensor reads and unbounded loops in runtime drivers. Explain that arbitrary custom C++ can bypass a software library and cannot be guaranteed safe by the IDE.
Document electrical and mechanical limits honestly. Motor power must come through a suitable driver and supply, not an ESP32 GPIO. Actual driver ratings, signal voltage compatibility, common-ground requirements, flyback protection, supply isolation, enable polarity, and boot pin behavior require component-specific validation. A provisional diagram is not a certified wiring instruction. Recommend initial motor tests with wheels raised, low duty limits, supervised power, and an accessible physical power disconnect. Define how a future physical emergency-stop input is integrated, but do not claim a software Stop button is a safety-rated emergency stop.
Create firmware tests and a physical test protocol for startup with motor power present, communication loss, application crash, stuck student logic, rapid direction reversal, invalid speed, unplug and reconnect, brownout or reset where safely testable, and physical stop operation where fitted. Record measured stop latency and observed output state for each exact hardware revision. Do not mark the motor subsystem physically verified until these tests actually run.

14 Curriculum contract for sixty substantive lessons
Deliver all sixty lessons below as actual content, not a list of titles or empty records. Organize them into ten modules of six lessons. Each lesson includes a stable ID, localized title and body, prerequisites, intended age or level, 30 to 60 minute default duration with adaptations, measurable objectives, required capabilities, safety notes, a clear explanation, a worked example, a guided activity, an independent challenge, expected observations, at least three assessment questions with answer explanations, troubleshooting, a teacher note, and a rubric or objective completion evidence. Motor and assembly activities require teacher-supervised variants.
Target at least 350 meaningful words of learner-facing English instruction per lesson, excluding code, repeated boilerplate, and answer keys; more is appropriate when needed. Supply equivalent complete Kazakh and Russian versions with technical meaning preserved. Each lesson must have its own substantive instructional objective and exercise. Do not inflate counts by duplicating lessons with renamed titles. Introductory noncoding lessons need a concrete inspectable artifact; coding lessons need executable starter and reference projects. Mark source solutions separately from student starters. A machine-readable content audit must enforce sixty unique IDs and required fields without pretending word count alone proves teaching quality.
Teach the following sequence. For each entry, implement the stated activity and evidence, then expand it into the complete lesson structure above.
Module 1 Getting started and safe investigation
L01 Exploring the studio. Teach the difference between Blocks, Code, Simulation, and Hardware. Have learners create, rename, save, close, and reopen a project. Evidence: a recovered project and a short explanation of which modes require a real board.
L02 Parts power and uncertainty. Identify controller, carrier, driver, actuator, sensor, and supply from the provisional kit inventory. Compare known specifications with unverified assumptions. Evidence: a completed component-role and power-path worksheet with unsafe connections correctly rejected.
L03 First block program. Build an LED or simulated indicator sequence using setup and loop concepts. Predict the state before running. Evidence: the saved blocks, generated C++, and an observation table that matches the sequence.
L04 Timing and sequences. Compare repeated waits with cooperative elapsed-time behavior. Create a two-indicator sequence and adjust its timing. Evidence: a trace showing the intended order and a reason that timing must not prevent stop handling.
L05 Serial messages as evidence. Send labeled messages from a sketch or simulator and inspect timestamps. Explain why printed text is not proof of motor movement. Evidence: a short exported log with the origin marked as hardware or simulation.
L06 First mini project. Design a traffic-signal or classroom timer using the previous concepts. Test at least three timing cases. Evidence: a portable project, observed results, and a short reflection on one defect found and fixed.
Module 2 Programming foundations
L07 Variables and units. Store time, sensor distance, and a speed request with explicit units. Change values and predict consequences. Evidence: a variable table and a working parameterized program without unexplained magic numbers.
L08 Arithmetic and mapping. Convert a bounded input range into a safe output range with clamping. Explore endpoints and out-of-range values. Evidence: five input-output tests including both limits and an explanation of saturation.
L09 Decisions and Boolean logic. Combine button and sensor conditions using AND, OR, and NOT. Build a decision table before coding. Evidence: a program that passes every row and a correction of one intentionally wrong condition.
L10 Loops and termination. Compare counted repetition, condition-controlled repetition, and endless event loops. Add a stop condition and execution budget. Evidence: a bounded challenge solution and identification of a loop that would otherwise run forever.
L11 Functions and reusable behavior. Extract repeated indicator or motion-intent patterns into parameterized functions. Discuss input ranges and side effects. Evidence: two call sites using one function and tests for normal and boundary arguments.
L12 Debugging a state machine. Model a three-state interactive system and diagnose a missing transition. Use logs rather than guesses. Evidence: a state diagram, a failing trace, the corrected program, and a passing regression case.
Module 3 Inputs outputs and calibration
L13 Buttons and debouncing. Observe simulated or measured contact bounce and compare raw versus debounced events. Evidence: one action per intentional press across ten trials and a justified debounce interval.
L14 Analog measurements. Read a compatible analog input or provided sensor model, inspect noise, and explain resolution and range. Evidence: a plotted series, correctly labeled units, and rejection of an incompatible voltage assumption.
L15 PWM and bounded outputs. Change indicator brightness using the selected profile's PWM capability. Discuss why duty cycle is not a guaranteed motor speed. Evidence: a tested bounded sweep and an explanation of its measurement limits.
L16 Sound and event feedback. Use a compatible buzzer driver or simulator sound event to signal states without blocking other work. Evidence: a timed event pattern that remains responsive to stop or cancel.
L17 Distance sensor behavior. Measure or simulate objects at several distances and handle out-of-range or missing readings. Evidence: a calibration table and a program that treats invalid data explicitly rather than as zero distance.
L18 Sensor dashboard. Combine two inputs with labeled serial telemetry and a local plot. Inject a disconnected-sensor condition. Evidence: readable exported data, units, and a visible fault state that does not invent measurements.
Module 4 Assembly and motor control
L19 Building a rover. Follow the two-wheel guide, check polarity and mechanical clearance, and record the chosen profile. Evidence: a completed inspection checklist and wiring map; physical claims require actual teacher observation.
L20 First safe motor test. With wheels raised and conservative limits, arm, command bounded motion, stop, and disarm. Use a simulated variant when hardware is absent. Evidence: separate startup, stop, and communication-loss results with their test mode recorded.
L21 Differential steering. Compare equal, unequal, and opposite wheel commands. Predict turning direction. Evidence: three trajectories and a documented correction if motor polarity differs from the profile convention.
L22 Speed ramping. Compare abrupt commands with bounded acceleration and a direction-change pause. Explain mechanical and electrical consequences. Evidence: a command trace showing the ramp and safe zero interval.
L23 Timed motion and uncertainty. Attempt a measured straight path and turn using time alone. Repeat trials and quantify variation. Evidence: a result table that explains why elapsed time does not guarantee distance.
L24 Calibrated square route. Tune a four-sided route in simulation and optionally on hardware. Separate geometry calibration from motor imbalance. Evidence: repeated endpoint errors and a justified parameter revision.
Module 5 Reactive robots
L25 Obstacle stop. Stop a rover before a configurable distance threshold and handle invalid sensor data conservatively. Evidence: near, far, missing-data, and threshold-boundary tests.
L26 Obstacle avoidance states. Implement move, stop, inspect, turn, and retry states without blocking safety servicing. Evidence: a trace through each state and a recovery case for a blocked route.
L27 Line sensor calibration. Compare light and dark surfaces or simulator reflectance values. Choose and justify thresholds. Evidence: calibration samples, selected limits, and an uncertain-reading strategy.
L28 Two-sensor line following. Implement a decision table for left, right, centered, and line-lost states. Evidence: completed cases and a line-lost stop or search behavior with a time bound.
L29 Proportional line control. Turn line error into a bounded steering correction and compare gains. Evidence: at least three gain trials and an explanation of oscillation or sluggish response.
L30 Course challenge. Combine line following and obstacle response with an explicit priority policy. Evidence: a repeatable course result and a test showing an obstacle interrupts line-following motion safely.
Module 6 Feedback and mechanisms
L31 Encoders and counting. Interpret pulses and direction through a compatible encoder adapter. Handle reset and overflow assumptions. Evidence: distance estimates for known counts and an explicit no-encoder alternative.
L32 Closed-loop wheel speed. Compare requested and measured speed and apply bounded proportional correction. Evidence: response plots for changing load in simulation or measured hardware data.
L33 Introductory PID. Add integral and derivative terms with output limits and integral windup protection. Evidence: controlled parameter comparisons and a reasoned choice, not a claim that one tuning suits all robots.
L34 Servo mechanisms. Set safe angle limits from the actual mechanism and avoid sustained force at end stops. Evidence: a limited sweep and fault handling for unsupported or absent servo hardware.
L35 Orientation estimates. Use an optional IMU or simulated orientation signal and explore noise, drift, and calibration. Evidence: labeled observations and a clear distinction between heading estimates and ground truth.
L36 Precision motion challenge. Combine available feedback to reach a target pose or actuate a mechanism. Evidence: repeated error measurements, limits, and a comparison with the timed-motion approach.
Module 7 Reading and writing Arduino C++
L37 From blocks to code. Trace blocks into includes, setup, loop, and runtime calls. Convert a copy to Code mode. Evidence: a mapping exercise and both preserved original blocks and independent edited source.
L38 Types and scope. Explore integers, floating-point values, Booleans, conversions, and variable lifetime. Evidence: a corrected sketch and boundary tests that reveal a truncation or scope mistake.
L39 Functions and interfaces. Write a small helper using documented parameters, return values, and failure handling. Evidence: compilation plus tests for valid and invalid inputs against the real runtime API.
L40 Nonblocking time. Replace a blocking delay sequence with elapsed-time states and account for timer rollover. Evidence: responsive stop handling and a simulated or unit-tested rollover case.
L41 Collections and telemetry. Record a bounded set of sensor samples and produce a compact structured message. Evidence: correct indexing, bounded memory, and handling of malformed or missing samples.
L42 Multi-file robot program. Split behavior, configuration, and helper logic into maintainable source files. Evidence: a real successful compile, meaningful diagnostics for an injected error, and a clean portable export.
Module 8 Simulation and experimental evidence
L43 Worlds and coordinates. Place a robot, obstacles, and goals in a coordinate system. Predict and inspect pose changes. Evidence: an exported world with correct geometry and labeled units.
L44 Repeatable experiments. Use deterministic seeds and fixed steps to compare two algorithms fairly. Evidence: matching repeated traces for the same seed and controlled variation when the seed changes.
L45 Collisions and boundary cases. Test wall contact, narrow passages, sensor range limits, and invalid starting poses. Evidence: a scenario suite and a corrected algorithm for one discovered failure.
L46 Noise and calibration transfer. Introduce sensor noise and compare simulator assumptions with observed hardware where available. Evidence: an uncertainty discussion and no unsupported claim of simulator-to-hardware equivalence.
L47 Automated challenge tests. Define start conditions, goals, timeout, and forbidden collisions as machine-checkable criteria. Evidence: a passing and failing program evaluated by the same scenario.
L48 Simulation investigation. Design an experiment comparing two navigation strategies across several worlds. Evidence: reproducible scenarios, results, and a conclusion bounded by the model's limitations.
Module 9 Engineering practice and classroom collaboration
L49 Requirements and test cases. Turn a robot mission into measurable behavior and failure conditions. Evidence: a small requirement-to-test matrix that includes a safe failure state.
L50 Diagnosing build errors. Investigate real missing-symbol, type, library, and board-selection errors using compiler output. Evidence: each corrected cause and a successful recompilation with saved logs.
L51 Devices and communication. Diagnose a busy port, wrong baud rate, unplug event, and incompatible firmware handshake. Evidence: a troubleshooting record identifying what the software can and cannot infer.
L52 Profiles and substitutions. Replace one sensor or motor-driver capability in a project and validate the new mapping. Evidence: a profile diff, conflict detection, and updated compatibility status.
L53 Sharing and reviewing. Export a submission package, import it into a teacher workspace, apply a rubric, and return feedback. Evidence: a complete offline round trip preserving IDs and excluding secrets.
L54 Responsible AI assistance. Ask for a hint, inspect shared context, verify a suggested code change, and reject an unsafe or unsupported answer. Evidence: a reviewed diff and independent compiler or test evidence.
Module 10 Capstone and demonstration
L55 Capstone proposal. Choose a feasible robot mission, available components, success criteria, and risks. Evidence: a scoped proposal with separate simulation and physical verification plans.
L56 Prototype and integration. Combine sensing, decisions, actuation, and telemetry in a minimal complete mission. Evidence: an integrated project with known limitations and passing component tests.
L57 Reliability and safety review. Inject communication loss, invalid readings, reset, and blocked movement where safely applicable. Evidence: observed safe states and an issue list with retest results.
L58 Performance improvement. Measure completion time, accuracy, or resource use and make one justified improvement. Evidence: comparable before-and-after trials without changing the acceptance rules midway.
L59 Technical documentation. Write assembly, operation, calibration, troubleshooting, and test evidence for another learner. Evidence: a peer following the instructions and a revision based on that attempt.
L60 Final demonstration. Present the mission, architecture, experiments, limitations, and reproducible project package. Evidence: a rubric-scored demonstration identifying exactly what was simulated, compiled, uploaded, and physically verified.

19 Security privacy and trust boundaries
Create a practical threat model covering imported projects, profiles and classroom archives, Markdown and SVG assets, build processes, serial input, AI responses, package downloads, and local credentials. Prevent path traversal, archive bombs, symlink or junction escapes, oversized content, arbitrary URL launches, and malicious IPC payloads. Validate canonical paths against user-authorized roots. Sanitize rendered content and constrain external URL schemes. Opening a project must not run it, compile it, install its dependencies, or execute hooks.
Compilation uses approved toolchains and known board recipes. Treat untrusted libraries, compiler plugins, scripts, and custom platform recipes as executable software requiring an explicit trust decision. Do not accept arbitrary CLI flags from an imported project. Limit background process privileges, lifetime, output size, and environment exposure. Building native source is not made safe solely by placing it in a folder; document remaining compiler and toolchain risks and use isolation where feasible.
Default to no analytics and no silent network requests. Keep logs bounded, redact credentials and unnecessary personal information, and offer an explicit diagnostic export preview. Store student data locally with documented locations and retention. Use actual protected credential storage, not reversible encoding presented as encryption. Include dependency and license inventories, a software bill of materials, and a vulnerability review process. Report unresolved material findings instead of suppressing security warnings for a green release badge.
20 Tests and reproducible evidence
Use a layered suite: unit tests for schemas, profile resolution, scheduling, protocol parsing, persistence, generation, and simulator math; integration tests for actual files, migrations, process handling, CLI compilation, content, and archive exchange; Electron end-to-end tests for installed-user flows; and separately labeled physical hardware tests. Test doubles are appropriate at unit boundaries but do not satisfy real CLI, device, or installed-application acceptance. Never rewrite assertions to accept a known defect merely to make CI pass.
Include meaningful negative tests: malformed profile, conflicting pins, invalid C++, missing library, stale build artifact, occupied COM port, unplug during upload, invalid firmware version, serial flood, malformed frames, timeout, AI failure, malicious archive, disk full, corrupted settings, interrupted migration, duplicate submission, and unavailable toolchain. For hardware-specific combinations unavailable in CI, state the compile coverage and remaining physical coverage separately. Cover the core lesson examples with at least one real reference FQBN and validate every declared supported combination in the release matrix. Use native or host-side firmware logic tests where possible, and supplement them with actual MCU and driver tests rather than confusing the two.
Use Playwright or an equivalent maintained Electron test approach for first launch, project creation, Blockly generation, code conversion, error navigation, save and reopen, simulation, lessons, language changes, classroom import and export, and a packaged-app smoke test. Require at least 80 percent branch coverage for non-UI domain modules and test all identified safety transitions regardless of the aggregate percentage. 21 Measurable acceptance criteria
AC01 Installation. A generated NSIS EXE installs, launches, upgrades, repairs or reinstalls as documented, and uninstalls on clean Windows 10 and Windows 11 x64 test environments. Standard-user installation works in its supported mode. No development server, Node installation, or repository checkout is required to launch the installed app.
AC02 Offline readiness. With network adapters disabled, the installed app opens lessons, all guide assets, documentation search, block and text editors, local projects, classroom packages, and every bundled simulator world. With the offline toolchain bundle imported, a known-good reference sketch compiles without contacting the internet.
AC03 Honest compilation. A valid sketch produces a real binary and build manifest; an intentionally invalid sketch fails with actual compiler diagnostics; a subsequent upload cannot reuse a stale artifact. The same checks pass from the packaged application under a path containing spaces and Cyrillic characters.
AC04 Hardware upload. On one identified supported physical reference board, the selected build is flashed using the real uploader and runtime identity is verified independently when the firmware supports it. Wrong selection, busy port, reset-related COM changes, and disconnection produce honest states. Without this test, hardware readiness remains blocked.
AC05 Profiles. At least two distinct board profiles and two interchangeable component-driver configurations exist with schema tests. A declarative new profile can be added without editor code changes when it uses existing drivers. Pin conflicts and unsupported capabilities prevent unsafe generation or upload, and unknown JECTIVE wiring stays visibly provisional.
AC06 Editors. Every shipping block has generation tests; workspace save and reload preserve semantics; generated examples compile; source diagnostics navigate to the right location; and Blocks-to-Code conversion preserves the original workspace without claiming arbitrary reverse conversion.
AC07 Simulator. All six required worlds load offline. The same program, world, and seed produce matching canonical traces across ten repeats on the same tested build. Pause and reset behave consistently; a runaway program can be stopped within 250 ms on the baseline machine. Unsupported C++ is rejected with a useful explanation.
AC08 Motor safety. Firmware startup is disarmed, invalid commands are rejected, speed and reversal limits are enforced, and tethered motion authority expires within the configured maximum 500 ms target. Physical measurements verify the stop behavior on each claimed motor configuration. A software-only test does not satisfy physical acceptance.
AC09 Content. Exactly sixty required lesson IDs have complete learner and teacher structures, three or more assessment questions each, compatible artifacts, and full EN, KK, and RU content. At least eight complete assembly guides and a searchable offline manual ship with zero broken internal links and zero missing required assets. Content checks compile applicable examples.
AC10 Classroom. Five learner workspaces complete two assignments through export, submission import, rubric grading, feedback, and CSV or print export while disconnected. Duplicate and conflicting submissions are handled explicitly. Reports contain real stored evidence and no invented activity.
AC11 Persistence. Forced termination during autosave and a migration failure recover without silently losing the last committed project. Backup and restore preserve projects, progress, and classroom records. Import rejects traversal and oversized archives; exports omit credentials and toolchain caches by default.
AC12 AI. Disabled and offline states are truthful. One configured real provider or local endpoint passes an integration test when credentials or service availability permit. Context preview, cancellation, redaction, and reviewed code application work. If a real provider test is unavailable, mark it NOT RUN and retain functional offline documentation search.
AC13 Localization and accessibility. Required catalogs have zero missing keys. A manual smoke test completes the main learner journey in all three languages, including Kazakh characters. Keyboard-only navigation reaches essential actions, focus is visible, and 100, 125, and 150 percent scaling do not obscure primary controls.
AC14 Performance. Measure on a declared baseline of Windows x64, four logical CPU cores, 8 GB RAM, and SSD storage. Target median cold launch at or below 8 seconds across five runs, a 500-block edit response p95 below 150 ms, and simulator display at or above 30 frames per second for bundled worlds. Idle working set should stay below 750 MB and show no sustained growth above 50 MB after warm-up during a 30-minute idle run. Report actual measurements and hardware; disclose misses instead of silently changing thresholds. Compiler duration is reported separately because it depends on the toolchain and cache.
AC15 Quality and security. Lint, type checks, required tests, content checks, and packaged smoke tests pass with recorded logs. Known critical exploitable release-path vulnerabilities or failed safety transitions block release. Test reports distinguish pass, fail, skipped, and not run. An installer file alone is not evidence that these gates passed.

23 Phased implementation and completion gates
Phase 0 establishes the repository, requirement matrix, hardware assumptions, threat model, profiles schema, selected compatible versions, test strategy, and a runnable packaged shell. Prove the application opens offline. Keep this phase brief enough to reach executable work quickly. A design document alone does not complete it.
Phase 1 delivers the first vertical slice: create a project, edit blocks, generate Arduino C++, save and reopen, invoke the actual CLI, surface a deliberate compiler error, and package the application. Gate: a known-good sketch really compiles from the packaged UI and a bad sketch really fails. Do not build dozens of empty screens before this works.
Phase 2 delivers device enumeration, explicit port selection, exclusive port ownership, real upload integration, serial monitoring, runtime handshake, and safe motor-driver abstractions. Gate: protocol and firmware tests pass; real board tests run when available and are otherwise explicitly blocked. Continue simulator and curriculum work even if physical hardware is unavailable.
Phase 3 delivers deterministic offline simulation, shared program semantics, source mapping, and provisional assembly content. Gate: representative programs run in the simulator and compile through the real pipeline, unsupported text programs are handled honestly, and six worlds pass their scenario tests.
Phase 4 delivers all sixty complete lessons, eight guides, offline manual, localization, persistent learner progress, and classroom export and review workflows. Gate: content validation, compile checks, localization completeness, and a full offline classroom round trip pass. A six-lesson sample is an intermediate milestone, not the requested final curriculum.
Phase 5 delivers configurable AI with context controls, full security hardening, accessibility work, migrations and recovery, performance measurements, and school deployment packaging. Gate: a real provider test where configured, malicious-input tests, offline smoke tests, and Windows installer tests have evidence.
Phase 6 completes regression testing, actual hardware verification for every hardware claim, release notes, deployment instructions, evidence audit, and final installer handoff. Keep partial milestones clearly labeled. If any mandatory gate cannot run, deliver useful artifacts and a precise outstanding-actions list, but do not call the entire product complete or production-ready.
24 Working method and final handoff
Maintain a traceable requirements matrix connecting each section and acceptance criterion to implementation files, tests, evidence, and remaining limitations. Use small verifiable increments. After each phase, record what works, what was tested, what failed, what is blocked, and the next concrete action. Update project documentation when APIs, profiles, file formats, or compatibility assumptions change. Persist a concise handoff file with the current commit or workspace state, commands that succeeded, open failures, and next steps so work survives context limits.
Do not silently reduce the scope to a web demo, simulator-only app, a pretty dashboard, an installer wrapping placeholders, or a curriculum outline. Do not claim arbitrary custom C++ is simulated, a provisional pinout is official, an AI reply is factual, or a successful compile proves safe physical operation. Protect learner work, explain limitations in the product where they matter, and keep the required workflows usable without internet.
Deliver the complete source repository, locked dependencies, build and test scripts, profile schemas and sample profiles, JECTIVE runtime and drivers, all curriculum and documentation assets, example projects, simulator worlds, classroom sample fixtures clearly labeled as samples, NSIS installer, offline toolchain resources, checksums, SBOM and licenses, and test evidence. Include exact developer setup, packaging, offline deployment, and hardware verification instructions. List known issues and any unexecuted tests with their prerequisites. Provide a compact final status table showing implemented, automatically tested, compiled, simulated, uploaded, and physically verified status separately.
Consult and verify the current official upstream references while implementing, then record the versions actually selected. Relevant starting points are Electron security at https://www.electronjs.org/docs/latest/tutorial/security, Arduino CLI configuration at https://docs.arduino.cc/arduino-cli/configuration/, Arduino CLI build behavior at https://github.com/arduino/arduino-cli/blob/master/docs/sketch-build-process.md, Blockly custom generators at https://docs.blockly.com/codelabs/custom-generator/the-basics/, Blockly serialization at https://docs.blockly.com/guides/configure/serialization/, ESP32 Arduino PWM at https://docs.espressif.com/projects/arduino-esp32/en/latest/api/ledc.html, and NSIS packaging at https://www.electron.build/nsis/. Begin by inspecting the repository and environment, documenting the provisional hardware assumptions, and building the first working vertical slice. Continue through the phases with real implementation and reproducible tests. The final objective is a usable, honest, maintainable desktop robotics studio that a school can install, teach with offline, and connect to explicitly supported real hardware once that hardware is validated.
