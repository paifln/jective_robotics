# Hardware assumptions and verification

The JECTIVE carrier revision, MCU variant, motor drivers, sensors, connectors and supplies are unknown. The JECTIVE Prototype remains unassigned and prevents hardware generation/compile/upload. No official pinout or electrical rating is invented.

Two separate Arduino reference definitions use ESP32 core 3.3.12: `esp32:esp32:esp32` for original ESP32, and `esp32:esp32:esp32c3` for C3. Neither implies S2/S3 or every module variant support. Original ESP32 assumes an external resistor-equipped indicator on GPIO2 (boot-sensitive); C3 assumes an external indicator on GPIO4. Onboard LEDs are not assumed. Check the real module exposure, flash/PSRAM, serial/USB and boot constraints before connection. C3's conservative profile reserves GPIO12–17 for flash, 18/19 for USB and 20/21 for console UART. Original ESP32 GPIO34+ listed inputs cannot drive outputs. ADC/Wi-Fi, peripheral bus and expert override handling remain incomplete.

Two experimental reviewed motor adapter families are direction/active-high-enable and dual-input H-bridge with all-low coast. They have different logical roles; actual driver standby, brake, enable polarity, voltage/current limits and flyback requirements must be verified. No supply comes from GPIO. Unsupported modules cannot borrow an assumed adapter. Pin validation is necessary, not sufficient evidence of electrical compatibility.

Runtime software design targets: boot disarmed, ±30% duty, duration up to 2000 ms, acceleration 40 duty percentage points/s, reversal zero interval 50 ms, tethered authority expiry 400 ms, independent 10 ms RTOS output task and physical stop input for autonomous mode. Host controls and cooperative generator integration remain unfinished. Host C++ tests and real two-board compilation pass; no measured output timing or electrical test has run.

COM3/COM4 here are Microsoft Bluetooth ports. Neither is an identified reference board. No port was opened or firmware uploaded automatically. Upload, handshake, motor start/stop, communication loss, reset/brownout, blocked student logic and physical stop cases are all **NOT RUN**.

Before physical acceptance record: board/module model, carrier revision, component part numbers, exact supply/grounding, logical pin map/hash, firmware binary/hash, date/operator, procedure and observed/measured results. Begin with controller-only checks, then raised wheels, low bounded duty, supervised power and reachable physical disconnect. Test startup power, malformed/duplicate/stale commands, unplug/crash, rapid reversal, stop input, reset and relevant safe fault cases for each exact driver configuration. Software Stop is not a safety-rated emergency stop. Never infer physical safety from compilation, simulator success or an upload.
