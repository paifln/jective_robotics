# Multi-file project services — current unpackaged foundation

The current source can preserve and compile real multi-file Code projects. The current renderer now adds per-file tabs, independently owned Monaco models with undo/view state, validated file creation, explicit deletion of helper files and compiler diagnostics that navigate to the selected file. L42 is not yet registered. The curriculum remains 41/60. Published installer 0.8.8 is unchanged and does not include this increment.

Projects retain their existing `source` entry sketch and may carry `sourceFiles` with up to fifteen additional flat `.h`, `.hpp` and `.cpp` files. Each additional file is limited to 100,000 characters; aggregate source remains bounded to 500,000 characters. Names reject traversal, path separators, streams, unsupported extensions, Windows device names and case-only collisions. Nonempty additional files are allowed only in Code mode. Existing single-source projects remain valid without migration; empty/absent files preserve their former build and activity fingerprints.

The actual toolchain writes every validated file into the operation's separate sketch directory. Canonical source hashes include filenames and contents, so a header/source change or rename invalidates upload reuse. Build manifests retain per-file hashes. Upload checks source snapshot names, expected contents, file type and size before calling the uploader; changed, missing or junction-replaced snapshots fail. Existing artifact/profile guards remain. Source/UI build acceptance compares all files, and board-upload status is reset by a file-map change.

Arduino export writes a complete temporary directory, then publishes a new `jective_sketch` folder with the matching entry-sketch name. It refuses an existing export/junction and does not merge into student files. A failed publish removes only the verified temporary directory. Tests inject filesystem failures and unexpected temporary locations to verify rollback and refusal before writing/deleting outside the intended export location. The export implementation is isolated from desktop dialogs.

Independent copies, SQLite projects/snapshots, validated backup and portable archive round-trips preserve every file. Saved-program activity counts header changes and ignores mere map reordering. A bounded compiler-log parser recognizes known project filenames and retains file/line/column/message; the renderer uses these records to open the corresponding model and reveal the exact line/column.

`node scripts/multifile-check.mjs` performs actual separate-file host compilation and execution with clock/Serial substitutes, actual ESP32 success and injected helper-error builds, portable archive round-trip and separate compilation of the exported Arduino directory. The injected error reports `behavior.cpp:6:34` and `unknownPhase`; the preceding build is rejected for upload after the failed rebuild. No serial upload occurs. The example has no GPIO/motor configuration.
