# Sound events and responsive simulation cancellation — unpublished work

The instruction model and Blockly now support a timed single-voice sound event (integer 20–20000 Hz, integer 1–60000 ms) and explicit sound stop. These are simulator events, not playback through a speaker or commands to an identified physical buzzer. Invalid values are rejected instead of clamped. Hardware generation reports SOUND_DRIVER_REQUIRED until a compatible driver and reviewed wiring exist.

Both indicator interpreters, including function calls, record event start time, frequency and duration without advancing program time. Subsequent messages and commands can execute at the same clock time. The robot simulator exposes an active virtual voice with its end timestamp. A new sound replaces the previous voice; stop clears it. Expiry is observed on the existing 20 ms simulation grid. A finite program with a pending sound remains running until expiry, so it cannot finish with a permanently orphaned virtual voice.

RobotSimulation.cancel() stops virtual wheels and sound, closes the instruction generator, clears active highlighting and latches cancelled status. Cancellation before the first step and during a long wait are supported. Future steps and repeated cancellation cannot resume the program. An execution fault also stops virtual sound. The worker accepts cancellation for its current operation ID; the renderer stops automatic stepping and displays the returned cancelled state. Pausing remains a separate operation that freezes the simulation clock.

The worker-response trace schema now validates event-specific types and bounds: sound needs a valid duration/frequency, PWM remains limited to 0–100%, indicator values are boolean, message values are strings, and channel/duration metadata cannot be attached to inappropriate event kinds. Sound block captions and the cancellation button have draft RU/KK translations.

Typecheck, lint, build and all 165 unit tests pass, with package branch coverage 1208/1288 (93.78%) and unchanged per-file thresholds. Tests cover nonblocking messages, voice replacement, grid expiry, explicit stop, faults, cancel-before-start, cancel-during-motion/wait, terminal idempotence, function execution, actual Blockly serialization and malformed worker events. Two targeted source Electron scenarios pass: new sound/cancellation behavior and L15 regression. The sound test opens an actual project, runs both workers, observes an immediate message, cancels a 60-second event/wait and verifies that subsequent stepping cannot reach the later message.

Snapshots are in `evidence/wip-sound-events/`. The preceding full 32-scenario source regression in `evidence/wip-L15/` predates sound changes and does not prove their full regression scope. L16 learner content is still outstanding; authored curriculum remains 15/60. Published 0.5.0 artifacts are unchanged. No physical buzzer, audible playback, upload, actuation or clean-machine acceptance is claimed.
