# 0.8.4 — Studio and independent student work

Studio now puts the program editor first. The introductory “Make your first program” journey has been removed. Its connections/program/simulator tabs use plain names. Open/save/compile retain accessible icon commands and tooltips. The visible **Run on board** button opens USB upload inside Studio, rather than sending the student away to a four-step tutorial. The same compact board component serves the dedicated board page: choose an enumerated USB port, compile, then upload and run. Upload replaces the existing firmware and the controller executes it after reset. This uses the existing real compiler/artifact validator and guarded uploader; it is not a simulator action. A missing port, unsupported profile/program, changed source or failed compilation disables upload. The native confirmation, concurrent-operation lock and post-confirmation port check remain in place.

The sidebar can collapse to icons with accessible names and hover titles. Its preference is stored locally and included in validated backup/restore. At 800 px and below, the mobile bottom navigation remains available. Extra indicator-trace tools have moved from the main command bar to result details. ESP32 is still named where selecting the actual hardware matters; routine commands now say “board”.

The header contains a 13-week green activity calendar. The displayed number is the number of active days in that window. The main process records successful explicit program saves, grouped by the Windows local date. A first saved program establishes activity; subsequent saves count only if its program fingerprint changes. Renaming, revision updates, block positioning, block IDs/comments, reopening, recovery autosave and unchanged repeat saves do not count. Code-mode text changes and block-command changes do count. This measures saved work, not knowledge, learning quality or teacher-verified achievement. Activity is local to this workspace, not a cloud account, and is limited to 3,660 retained dates and 10,000 program fingerprints. Fingerprints contain hashes rather than additional copies of source code.

The simulator runs the current Studio blocks directly. “My program” and the four example-program buttons are removed from its student screen. The main controls are field selection, run, pause and reset. Single stepping, simulated button input, cancellation and export remain available under testing tools; validated scenario editing and state details are retained. There are 12 fields: the previous six plus slalom, parking, square track, narrow passage, warehouse and a turn before a wall. Their actual geometry and deterministic execution are tested. This is still a block-program simulator; arbitrary edited C++ requires the hardware compiler.

The student assistant has a question, optional code sharing, answer and explicit reviewed-code workflow. It no longer shows endpoint/provider/model/key configuration or raw project metadata previews. **Help → Administrator: configure assistant** contains workspace OpenAI model/key setup. This is UI separation, not an administrator authentication boundary: anyone with access to this Windows workspace can open Help. The student chat is available only for enabled official OpenAI configuration with an encrypted key. The key is never returned to the renderer. No key was provided and no actual OpenAI network answer was verified in this revision. Local hints continue to work offline. Suggested changes still require explicit review and application to a preserved Code copy, and do not automatically compile or upload.

## Architecture and verification

`packages/persistence/activity.ts` owns validated, bounded activity data and semantic program fingerprinting. `WorkspaceStore.completedSave` commits the saved project, recovery pointer, snapshot and activity together in one SQLite transaction, after the project file write succeeds. A failed/cancelled file write cannot reach that transaction. Transaction rollback is tested. Activity and the sidebar preference use strictly validated settings keys, retaining the existing seven-table/user-version-1 schema and compatibility with old backups. IPC remains origin guarded, typed and result validated. UI modules `ActivityCalendar`, `AssistantSetup` and `StudentBoard` keep presentation separate from persistence, AI transport and hardware operations.

Evidence is in `evidence/studio-workspace`. The final report records actual checks and the installer hash. Tests cover successful/unchanged/metadata-only saves, local days, bounded histories, semantic block comparisons, recovery exclusion, reopening, backup restoration, rollback, all 12 simulator worlds and the student UI. Targeted Electron checks additionally cover actual ESP32 C++ compilation, invalid-source rejection, build invalidation, upload confirmation locking, isolated IPC, resource restrictions, Code-copy preservation, lessons, themes and small-screen navigation. The complete legacy Electron suite is not claimed as migrated or run.

Windows 10 acceptance, actual installer installation/uninstallation and physical ESP32/JECTIVE upload and motor/sensor connections remain **NOT RUN**. The host is Windows 11 build 26200. Integrated motor blocks still lack a verified JECTIVE hardware driver/pinout and remain simulator-only; the board screen reports this rather than inventing support. The installer is unsigned. The broader original master prompt remains incomplete, including L37–L60 and independent language review; these interface changes do not claim to complete those requirements. See the physical and clean-machine acceptance steps in [0.8.3](RELEASE-0.8.3.md).

Final checks: typecheck/lint/build pass; **320/320 unit/integration tests**, **6/6 targeted Electron scenarios**, zero skips/flakes and **96.15% branch coverage**, with the per-file 80% gate passed. The dependency audit reports zero known vulnerabilities. Packaged binary fuses, exact tested-build file equality, renderer startup, duplicate-instance rejection and intentional ASAR tamper rejection pass; the archive was restored and its hash verified.
